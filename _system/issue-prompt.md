# Sunday AI newsletter: editorial production instructions

**GitHub:** KarterGIT/newsletter-vault (main). **Schedule:** Sunday at 5 PM Eastern. **Project Week 1:** October 5–11, 2026; increment by seven days, never use ISO W41/W42.

1. Read `Newsletter Template.md` first for the current **reader-facing writing standard** and format. Read `_system/sources.md`, the current `Week N/Week N.md` hub, all verified files in `Week N/Sources/`, and the previous newsletter if available.
2. Select genuinely important, distinct stories. An editor's `[x] keep` takes priority if facts remain verifiable. Reopen original articles, check publication dates, names, quantities, attribution and original links. Cross-check significant controversial claims where possible. Exclude Reddit, questionable aggregators, and unverified items. Do not pad categories or force a target story count.
3. Write a **publication-style newsletter**, not source notes or a catalog of repetitive summaries. Aim for ~900–1,300 words when the news supports it. Give it an engaging original headline, one-sentence standfirst, natural introductory hook, 3–4 linked highlights, and 5–8 selective stories under relevant established Technical, Jobs, Broader social impact, China/open weights, and Regulation/politics headings. Use a range of section/story lengths, varied transitions, and a strong closing perspective. Explain jargon naturally and reader consequences in the prose, instead of stamping every item with `What this means:`. Use original, non-hyped wording and embedded clickable **external** source links.
4. Preserve source nuance: attribute developers' own claims, preliminary figures, study limitations, forecasts and commentary rather than asserting them as settled fact. Verify every linked claim and make a final quality pass for readability and coherence.
5. Save one new `Week N/Newsletter Draft.md` with YAML `type: newsletter-issue`, `project_week: N`, `status: draft`, blank `reviewed_by:`. Keep main newsletter prose clean enough to paste into a website with minimal editing. Put relative Markdown source-note links and the weekly overview link **in a clearly separate editorial-only appendix or hidden comment** at the end, not throughout public-facing prose. The weekly overview links directly to the issue. Use standard relative Markdown links with spaces encoded as `%20`, not editor-specific wikilinks.
6. Never post, email, or publish without human approval, overwrite an existing draft, or create an empty placeholder. After writing, verify the GitHub file by reading it back. Update only the `<!-- WEEK FILES START -->` to `<!-- WEEK FILES END -->` region in `Week N/Week N.md` with the real draft link, keeping human notes intact. Do not modify any standalone `Tests/` files.
7. Report the draft's direct link, story count, verification limitations and whether any publication preparation remains. If GitHub is blocked, return the full newsletter text and clearly report that no commit succeeded.

Keep Week N structure: central `Newsletter Template.md` -> `Week N/Week N.md` -> up to three dated source pulls and one complete newsletter draft.
